# Авито.Кухня

«Авито.Кухня» — MVP-платформа для заказа еды. Она предоставляет API для
веб-клиента и интеграционный API для заведений-партнёров. Отдельный сервис
заведения в этом репозитории демонстрирует полный сценарий интеграции.

## Границы MVP

Первая версия поддерживает полный сценарий оформления заказа:

1. Пользователь просматривает доступные заведения и их меню.
2. Пользователь создаёт заказ из одного заведения.
3. Платформа проверяет актуальную доступность товаров и фиксирует их цены.
4. Заведение принимает или отклоняет заказ через интеграционный API.
5. Пользователь отслеживает дальнейшие изменения статуса заказа.

Аутентификация, обработка платежей, курьерская логистика, промокоды, рейтинги,
полнотекстовый и географический поиск намеренно не входят в двухдневный MVP.
Точки расширения и компромиссы для промышленной эксплуатации будут описываться
по мере разработки системы.

## Планируемая архитектура

- **API платформы:** Python, FastAPI, Pydantic и `asyncpg` с явными SQL-запросами.
- **Сервис заведения:** отдельное FastAPI-приложение, имитирующее одного партнёра.
- **База данных:** PostgreSQL с версионируемыми SQL-миграциями.
- **Интеграция:** синхронные HTTP-команды и идемпотентные обратные вызовы для
  обновления статусов со стороны заведения.
- **Запуск:** Docker Compose.
- **Качество:** Ruff, mypy, pytest и интеграционные HTTP-тесты.
- **Документация:** генерируемая OpenAPI-спецификация и исходники Mermaid для
  диаграмм C4, ER и CJM.

Подробные архитектурные решения и инструкция локального запуска будут
добавляться вместе с соответствующей реализацией, чтобы документация оставалась
исполняемой и соответствовала коду.

- `services/kitchen-api` — основной API платформы.
- `services/restaurant-api` — пример интеграции заведения.
- `migrations` — версионируемые SQL-миграции общей базы данных.
- `tests` — автоматические тесты бизнес-сценариев и HTTP-контрактов.

- `openapi` — зафиксированная OpenAPI-спецификация.

## Локальная разработка

Требуется Python 3.12 или новее. Установите проект вместе с инструментами
разработки и запустите проверки:

```bash
python -m pip install -e ".[dev]"
ruff check .
mypy
pytest
```

Запуск HTTP-сервера с автоматической перезагрузкой:

```bash
uvicorn avito_kitchen.main:app --reload
```

После запуска проверка состояния доступна по адресу
`GET http://127.0.0.1:8000/api/v1/health`, а Swagger UI — по адресу
`http://127.0.0.1:8000/docs`.

## Запуск в Docker Compose

Скопируйте `.env.example` в `.env`, если хотите изменить демонстрационные
настройки, затем выполните:

```bash
docker compose up --build
```

Compose сначала дожидается PostgreSQL, затем отдельным контейнером применяет
SQL-миграции и только после его успешного завершения запускает API. Проверка
готовности приложения с запросом к базе данных доступна по адресу
`GET http://127.0.0.1:8080/api/v1/ready`. Внешний порт можно изменить через
переменную `API_PORT`.

## Пользовательский API

- `GET /api/v1/restaurants` — список активных заведений с фильтром `name` и
  параметрами пагинации `limit`, `offset`.
- `GET /api/v1/restaurants/{restaurant_id}/menu` — меню заведения. По умолчанию
  возвращаются только доступные позиции; параметр `available_only=false` полезен
  для демонстрации временно отсутствующих блюд.

Цены передаются целым числом `price_minor`: например, `39000` означает 390 рублей
для валюты `RUB`.

### Заказы

- `POST /api/v1/orders` — оформить заказ. Обязателен заголовок
  `Idempotency-Key`; безопасный повтор того же запроса возвращает исходный заказ.
- `GET /api/v1/orders/{order_id}?customer_id={customer_id}` — получить заказ,
  если он принадлежит указанному временному идентификатору пользователя.

При оформлении платформа повторно проверяет доступность всех блюд, блокирует их
на время транзакции и сохраняет снимки названий и цен. Если хотя бы одно блюдо
недоступно, весь запрос завершается с `409 Conflict` без частичного заказа.

### API заведения

Закрытые маршруты требуют заголовок `X-Partner-Token`. В MVP токен связывается
с одним демонстрационным заведением через переменные окружения.

- `GET /api/v1/partner/orders?status=created` — очередь заказов заведения.
- `PATCH /api/v1/partner/orders/{order_id}/status` — принять, отклонить или
  обновить этап приготовления заказа.

Разрешённые переходы: `created → accepted/rejected`, `accepted → preparing`,
`preparing → ready`. Повтор уже выполненного перехода безопасен и не создаёт
дубликат в истории статусов.

Демонстрационный Restaurant API доступен на `http://127.0.0.1:8081/docs`. Он
получает очередь и меняет статусы исключительно через HTTP-вызовы Kitchen API,
не имея доступа к PostgreSQL.
