# Авито.Кухня

MVP API-платформы заказа еды с отдельным демонстрационным сервисом заведения.
Проект реализован на Python 3.12, FastAPI, PostgreSQL 17 и чистом SQL без ORM.

Репозиторий показывает полный сценарий: пользователь выбирает блюда и создаёт заказ,
заведение получает его через закрытый API, принимает и последовательно переводит в
состояния `preparing` и `ready`, а пользователь видит актуальный статус.

## Быстрый запуск

Требуются Docker и Docker Compose. Файл `.env` создавать необязательно: для демонстрации
у Compose есть безопасные локальные значения по умолчанию.

```bash
docker compose up --build --detach
docker compose ps
```

При первом запуске Compose выполняет следующую последовательность:

1. запускает PostgreSQL и ожидает его готовности;
2. применяет версионируемые SQL-миграции отдельным контейнером;
3. запускает Kitchen API и проверяет соединение с базой;
4. запускает Restaurant API после готовности платформы.

После запуска доступны:

| Назначение | Адрес |
|---|---|
| Swagger Kitchen API | <http://127.0.0.1:8080/docs> |
| OpenAPI Kitchen API | <http://127.0.0.1:8080/openapi.json> |
| Readiness Kitchen API | <http://127.0.0.1:8080/api/v1/ready> |
| Swagger Restaurant API | <http://127.0.0.1:8081/docs> |
| Health Restaurant API | <http://127.0.0.1:8081/health> |

Остановить окружение без удаления данных:

```bash
docker compose down
```

## Сквозной демонстрационный сценарий

Все команды выполняются после запуска Compose. В миграции уже создано демонстрационное
заведение с доступными блюдами.

### 1. Посмотреть каталог и меню

```bash
curl http://127.0.0.1:8080/api/v1/restaurants
curl http://127.0.0.1:8080/api/v1/restaurants/10000000-0000-4000-8000-000000000001/menu
```

### 2. Создать заказ

```bash
curl -i -X POST http://127.0.0.1:8080/api/v1/orders \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: demo-order-001" \
  -H "X-Request-ID: readme-demo-001" \
  -d '{
    "customer_id": "30000000-0000-4000-8000-000000000001",
    "restaurant_id": "10000000-0000-4000-8000-000000000001",
    "delivery_address": "ул. Примерная, 1",
    "items": [
      {
        "menu_item_id": "20000000-0000-4000-8000-000000000001",
        "quantity": 2
      }
    ]
  }'
```

Скопируйте поле `id` из ответа в `ORDER_ID` в следующих командах. Повтор запроса с тем же
телом и `Idempotency-Key` вернёт исходный заказ с `200 OK`. Тот же ключ с другим телом
вернёт `409 Conflict`.

### 3. Обработать заказ со стороны заведения

Restaurant API не обращается к PostgreSQL и выполняет операции только через закрытый
Kitchen API.

```bash
curl "http://127.0.0.1:8081/api/v1/orders?status=created"
curl -X POST "http://127.0.0.1:8081/api/v1/orders/ORDER_ID/accept"
curl -X POST "http://127.0.0.1:8081/api/v1/orders/ORDER_ID/preparing"
curl -X POST "http://127.0.0.1:8081/api/v1/orders/ORDER_ID/ready"
```

### 4. Проверить результат со стороны пользователя

```bash
curl "http://127.0.0.1:8080/api/v1/orders/ORDER_ID?customer_id=30000000-0000-4000-8000-000000000001"
```

Итоговый статус должен быть `ready`. Для ветки отказа создайте новый заказ и вызовите
`POST /api/v1/orders/{order_id}/reject` в Restaurant API.

## Пользовательские сценарии

- поиск активного заведения по названию с offset-пагинацией;
- просмотр доступных позиций меню;
- атомарное создание заказа из одного заведения;
- отказ от всего заказа, если хотя бы одна позиция стала недоступна;
- безопасный повтор создания заказа по `Idempotency-Key`;
- чтение заказа только с соответствующим `customer_id`;
- отслеживание результата обработки заведением.

Сценарии и проблемные ветки визуализированы в
[`docs/cjm-user.puml`](docs/cjm-user.puml).

## Сценарии заведения

- чтение собственной очереди с фильтром по статусу;
- аутентификация стандартным `Authorization: Bearer <token>`;
- принятие или отклонение нового заказа;
- переходы `created → accepted → preparing → ready`;
- безопасный повтор уже применённого перехода;
- отклонение недопустимого перехода с `409 Conflict`;
- сохранение истории каждого изменения статуса.

CJM партнёра находится в [`docs/cjm-restaurant.puml`](docs/cjm-restaurant.puml).

## Архитектура

В репозитории находятся два независимо запускаемых HTTP-сервиса:

- **Kitchen API** — владелец каталога, заказов и машины состояний;
- **Restaurant API** — пример внешней системы заведения, использующий Kitchen API по HTTP.

Kitchen API разделён на слои:

```text
presentation/http → application → domain
                         ↓
                 infrastructure
```

- `presentation/http` отвечает за HTTP-контракт, валидацию и преобразование ошибок;
- `application` координирует бизнес-сценарии через протоколы репозиториев;
- `domain` содержит модели, ошибки и допустимые переходы состояния;
- `infrastructure` реализует репозитории на `asyncpg` и явном SQL.

Такое разделение позволяет тестировать сценарии без базы данных и заменять транспорт или
хранилище без переноса бизнес-правил. C4 Level 2 находится в
[`docs/c4.puml`](docs/c4.puml), ER-схема — в
[`docs/database.puml`](docs/database.puml).

## Ключевые технические решения

### Чистый SQL и транзакционные границы

ORM намеренно не используется. SQL расположен в PostgreSQL-репозиториях, а создание заказа
выполняется одной транзакцией. Строки выбранных позиций блокируются через `FOR UPDATE`,
после чего повторно проверяются принадлежность заведению и доступность. Заказ, его позиции,
начальная история статуса и ключ идемпотентности фиксируются атомарно.

### Деньги и историчность

Суммы хранятся целыми числами в минимальных единицах валюты: `39000` для `RUB` означает
390 рублей. В `order_items` сохраняются снимки названия и цены, поэтому последующее
изменение меню не переписывает историю заказа.

### Идемпотентность

Область действия и ключ образуют первичный ключ таблицы `idempotency_keys`. SHA-256 от
нормализованной команды отличает безопасный повтор от попытки использовать ключ с другими
данными. Переход статуса также идемпотентен: повтор текущего состояния не создаёт запись в
истории второй раз.

### Конкурентное изменение статусов

Партнёрский репозиторий блокирует заказ `SELECT ... FOR UPDATE`, проверяет переход и меняет
статус вместе с историей в одной транзакции. Два параллельных обработчика не смогут
применить несовместимые переходы к одному состоянию.

### Связь с пользователями и заведениями

По условию задания авторизация пользователей не реализуется. `customer_id` моделирует
будущий идентификатор субъекта и уже участвует в проверке владения заказом. Внешние
идентификаторы заведений и блюд отделены от внутренних UUID платформы. Партнёрский токен в
MVP связан с одним заведением через конфигурацию.

## API и данные

Основные маршруты Kitchen API:

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/health` | Проверка HTTP-процесса |
| `GET /api/v1/ready` | Проверка соединения с PostgreSQL |
| `GET /api/v1/restaurants` | Каталог заведений |
| `GET /api/v1/restaurants/{id}/menu` | Меню заведения |
| `POST /api/v1/orders` | Создание заказа |
| `GET /api/v1/orders/{id}` | Получение заказа пользователя |
| `GET /api/v1/partner/orders` | Очередь партнёра |
| `PATCH /api/v1/partner/orders/{id}/status` | Переход статуса партнёром |

Зафиксированные спецификации OpenAPI 3.1 находятся в
[`openapi/kitchen-api.json`](openapi/kitchen-api.json) и
[`openapi/restaurant-api.json`](openapi/restaurant-api.json). Тест проверяет, что они не
расходятся с приложениями. После намеренного изменения контракта выполните `make openapi`.

Миграции применяются в лексикографическом порядке и регистрируются в служебной таблице
`schema_migrations`:

- `001_initial_schema.sql` — таблицы, связи, ограничения и индексы;
- `002_demo_catalogue.sql` — воспроизводимые демонстрационные данные.

## Ошибки и диагностика

Оба сервиса принимают необязательный `X-Request-ID`. Допустимый идентификатор возвращается
в ответе, иначе генерируется UUID. Каждый запрос журналируется однострочным JSON с методом,
путём, статусом и длительностью. Уровень задаётся через `LOG_LEVEL`.

Единый формат ошибки:

```json
{
  "error": {
    "code": "not_found",
    "message": "Заведение не найдено",
    "details": null,
    "request_id": "c09c41a1-4905-4ac6-a60b-603bffc7c758"
  }
}
```

Необработанные исключения возвращают обобщённое сообщение без внутренних деталей, но
записываются в журнал с request-id.

## Локальная разработка и проверки

Требуется Python 3.12 или новее:

```bash
python -m pip install -e ".[dev]"
make check
```

Эквивалент без `make`, в том числе для PowerShell:

```bash
ruff check .
ruff format --check .
mypy
pytest
```

Полезные команды:

| Команда | Действие |
|---|---|
| `make up` | Собрать и запустить окружение в фоне |
| `make logs` | Следить за журналами контейнеров |
| `make migrate` | Запустить мигратор вручную |
| `make openapi` | Обновить обе OpenAPI-схемы |
| `make e2e` | Запустить изолированный сквозной тест с отдельной PostgreSQL |
| `make e2e-down` | Удалить контейнеры и временные данные E2E-окружения |
| `make down` | Остановить окружение без удаления volume |

### Изолированные E2E-тесты

E2E-окружение имеет собственное имя Compose-проекта, сеть и PostgreSQL на `tmpfs`. Оно не
публикует порты и не использует volume обычного приложения. Тестовый контейнер проверяет
миграции, каталог, атомарный отказ для недоступного блюда, идемпотентный повтор и конфликт
ключа с другим телом, изоляцию заказа по `customer_id` и полный межсервисный переход до
`ready`.

```bash
make e2e
make e2e-down
```

Прямой эквивалент первой команды:

```bash
docker compose -f docker-compose.e2e.yml up --build \
  --detach --wait restaurant-api-e2e
docker compose -f docker-compose.e2e.yml run --build --rm tests-e2e
```

Обычный `pytest` исключает маркер `e2e`, поэтому быстрые тесты не требуют Docker.

## Осознанные упрощения MVP

- нет регистрации и аутентификации пользователей согласно условию задания;
- один статический партнёрский токен вместо кабинета и ротации credentials;
- Restaurant API опрашивает очередь, webhooks и брокер сообщений не добавлены;
- нет платежей, курьерской логистики, отмены пользователем и расчёта времени доставки;
- нет API управления меню: демонстрационный каталог загружается миграцией;
- offset-пагинация достаточна для MVP, но не для глубоких страниц большого каталога;
- причина отказа заведения не хранится отдельным полем;
- таблица идемпотентности не очищается по TTL;
- метрики и distributed tracing не подключены, оставлены JSON-логи и request-id.

Эти ограничения уменьшают объём двухдневного задания, не нарушая заявленные сквозные
сценарии.

## Путь масштабирования

1. Заменить статический токен на API-ключи с хешированием, ротацией, областью прав и
   привязкой к нескольким заведениям.
2. Добавить outbox в транзакцию заказа и асинхронную доставку событий через Kafka;
   Restaurant API сможет получать webhook, а polling останется резервным механизмом.
3. Вынести каталог в отдельный сервис и добавить полнотекстовый/географический поиск;
   для выдачи перейти на cursor-пагинацию и кэширование.
4. Разделить заказ и доставку на отдельные bounded context, сохранив платформенный UUID и
   версионируемые события как интеграционный контракт.
5. Партиционировать заказы и историю по времени или заведению, добавить read-replica для
   пользовательских чтений и архивирование ключей идемпотентности.
6. Добавить OpenTelemetry, RED-метрики, алерты, секрет-хранилище и ограничение частоты
   запросов на границе API.

## Допущения

Демонстрационные UUID фиксированы только для воспроизводимого сценария. Значения `.env.example`
не предназначены для промышленной эксплуатации. Статусы `delivering`, `completed` и
`cancelled` зарезервированы схемой БД как точки расширения, но реализованный партнёрский
сценарий заканчивается на `ready`.
